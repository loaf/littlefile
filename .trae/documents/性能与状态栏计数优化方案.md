# 性能与状态栏计数优化方案（/plan）

## Summary

目标：
- 导入超大规模文件（>2万）时，主界面列表滚动/搜索/排序响应更快。
- 点击列头排序时“立即重排并回到顶部”，且不出现长时间无反馈。
- 状态栏文件数在有筛选时显示“当前/总计”，并且总计在导入/删除后保持准确。

范围：
- 分析当前实现瓶颈，并给出可落地的改进建议与具体改动点（前端 + Rust/SQLite）。

## Current State Analysis（基于现有代码）

### 1) 列表分页/虚拟滚动
- 列表采用无限滚动 + `@tanstack/react-virtual`，一次加载 `PAGE_SIZE=50`，滚动接近底部触发加载更多：[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx#L51-L55)、[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx#L236-L244)。
- 后端使用 `LIMIT ? OFFSET ?` 分页：[files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs#L159-L177)。

风险点：
- `OFFSET` 在大偏移量时会明显变慢（SQLite 常见问题：需要跳过大量行）。

### 2) 排序点击“更慢”的直接原因（当前实现缺少重拉取）
- 排序状态在 `useFiles` 内部维护（`sortBy/sortOrder`），但 `LibraryList` 的数据重载 effect 只依赖 `filter`：[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx#L42-L46)。
- 因此点击表头更新 `sortBy/sortOrder` 后，通常不会立即触发 `fetchFiles(0, ...)`，用户体感为“点了但没反应/很慢”。

### 3) 每次加载都做“总数统计 + 数据查询”，成本偏高
- `list_files` 每次调用都会：
  - 执行一次 `COUNT(DISTINCT f.id)`（并带 LEFT JOIN tags/file_tags）：[files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs#L144-L157)
  - 执行一次数据查询（LEFT JOIN + GROUP_CONCAT + GROUP BY + ORDER BY）：[files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs#L159-L173)

风险点：
- 无限滚动每翻一页（50 条）都会重复统计总数；在导入写入期（大量 INSERT）叠加 mutex 争用，会进一步放大延迟。

### 4) “导入中/导入后都慢”的核心结构性原因：单连接 + 全局 Mutex 串行化
- Rust 侧数据库连接以 `state.db.lock()` 方式获取（import / list_files / library_info 等都需要），导致读写请求在应用层被串行化。
- 即使 SQLite WAL 支持并发读写，也会被这把 mutex 抹平并发收益。

### 5) 状态栏“总文件数不准确”的根因
- 状态栏显示的 `totalFiles` 来自 `libraryInfo.total_files`：[App.tsx](file:///d:/dev/littlefile/src/App.tsx#L99-L107)、[StatusBar.tsx](file:///d:/dev/littlefile/src/components/common/StatusBar.tsx#L43-L56)。
- `libraryInfo` 只在打开库或手动 `refreshInfo()` 时更新：[useLibrary.ts](file:///d:/dev/littlefile/src/hooks/useLibrary.ts#L11-L26)。
- 导入完成时 App 仅 `setRefreshKey` 让列表重挂载，**没有**刷新 `libraryInfo`：[App.tsx](file:///d:/dev/littlefile/src/App.tsx#L47-L49)；删除文件同理只刷新列表，不刷新库统计：[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx#L159-L173)。

结果：
- 导入/删除后状态栏的“总计”会滞后，表现为“不准确”。
- 目前也没有把“筛选后的总数（useFiles.totalCount）”传到状态栏，因此筛选时无法显示“当前/总计”。

### 6) 索引与查询形态
- 现有索引：filename/author/sha256/created_at、file_tags(tag_id,file_id)：[schema.rs](file:///d:/dev/littlefile/src-tauri/src/db/schema.rs#L53-L61)。
- `size` 可排序但无索引；`LIKE '%q%'` 无法利用索引，数据量增大时搜索更慢：[files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs#L74-L94)。

## Proposed Changes（建议与实施步骤）

按“收益/风险/工作量”分三档，建议先做 Quick Wins，再做结构优化。

### A. Quick Wins（优先做，改动小但立竿见影）

1) **排序点击立即生效并回到顶部**
- 文件：[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx)
- 做法：
  - 让数据重载 effect 同时依赖 `filter + sortBy + sortOrder`（或依赖 `fetchFiles` 引用变化），并在排序变化时：
    - `setLoadedOffset(0)`
    - `fetchFiles(0, PAGE_SIZE, filter)`（覆盖）
    - `setLoadedOffset(PAGE_SIZE)`
    - 可选：`clearSelection()`，避免排序后选择错位
- 验收：点击任意可排序列，列表立即按新排序展示，并滚动回顶部。

2) **状态栏显示“当前/总计”，并保证总计实时**
- 文件：
  - [App.tsx](file:///d:/dev/littlefile/src/App.tsx)
  - [StatusBar.tsx](file:///d:/dev/littlefile/src/components/common/StatusBar.tsx)
  - [useLibrary.ts](file:///d:/dev/littlefile/src/hooks/useLibrary.ts)
  - [LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx)
- 做法（两部分）：
  - 总计准确：
    - 在 `handleImportComplete` 里调用 `refreshInfo()`（而不仅仅是 `setRefreshKey`）。
    - 在删除文件/批量删除后，也触发 `refreshInfo()`（可通过在 LibraryList 增加回调 `onMutateDone` 通知 App）。
  - 当前数量：
    - 将 `useFiles.totalCount` 通过 `LibraryList` 向上传递（例如 `onTotalCountChange(totalCount)`），App 维护 `filteredTotalCount` 状态；
    - StatusBar 渲染为：`{filteredTotalCount} / {libraryInfo.total_files} 个文件`（当无筛选时两者相等）。
- 验收：
  - 导入完成后状态栏总数立刻更新。
  - 删除文件后状态栏总数立刻更新。
  - 搜索/筛选后状态栏显示“当前/总计”，且“当前”与列表的分页总数一致。

3) **减少不必要的重渲染/不稳定更新**
- 文件：[LibraryList.tsx](file:///d:/dev/littlefile/src/components/library/LibraryList.tsx)
- 做法：
  - 修正 `EditableDescriptionCell` 在 render 期间触发 `setState` 的写法，改为 `useEffect` 同步外部值（仅在非编辑态时同步），避免大列表下额外渲染与潜在抖动。
- 验收：滚动/加载更多时 CPU 占用下降，描述列不出现闪烁。

4) **把“总数统计”从每页加载中剥离**
- 文件：
  - [useFiles.ts](file:///d:/dev/littlefile/src/hooks/useFiles.ts)
  - [files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs)
- 两种实现路线（二选一，推荐第 1 种）：
  1. 后端加参数 `includeTotal: bool`，只有 `offset==0` 或显式请求时才执行 count；后续加载更多只查数据。
  2. 后端保持不变，但前端在加载更多时不再依赖 totalCount（只用 `files.length` 与上一轮 totalCount 的缓存判断是否继续加载）。
- 验收：加载第 2、3、… 页时后端不再做 count 统计，明显减少 IO/CPU。

### B. Medium（中期优化，解决 2 万+ 的系统性性能问题）

5) **为排序字段补齐索引**
- 文件：[schema.rs](file:///d:/dev/littlefile/src-tauri/src/db/schema.rs)
- 做法：
  - 增加 `idx_files_size`（以及必要时 `idx_files_filename`/`idx_files_author` 与排序 collation 一致性检查）。
- 兼容性：
  - 需要做一次 migration（项目已有 migrations 目录）。
- 验收：按 size 排序时明显更快，且导入后仍可用。

6) **优化 list_files 的 SQL 形态**
- 文件：[files.rs](file:///d:/dev/littlefile/src-tauri/src/commands/files.rs)
- 做法建议：
  - `COUNT` 查询：当未使用 `tag_ids/has_tags` 等需要 tags 的条件时，避免 LEFT JOIN 与 DISTINCT（直接 `COUNT(*) FROM files WHERE ...`）。
  - 数据查询：考虑改为“主表分页 + 子查询聚合 tags”，减少 `GROUP BY` 在大表下的开销（尤其配合 limit=50）。
- 验收：无标签筛选时，查询计划更简单；整体延迟下降。

7) **用 Keyset Pagination 替代 OFFSET（可选但推荐）**
- 适用：当用户经常滚动到很深的位置时（offset 很大）。
- 做法：
  - 前端加载更多不再传 offset，而传“上一页最后一条记录的排序键 + id”（seek）。
  - 后端 WHERE 增加“(sort_col, id) > (last_sort_val, last_id)”语义（按 asc/desc 分别处理）。
- 验收：滚动越深也不会明显越来越慢。

### C. Long-term（长期方案，针对更大规模与更复杂搜索）

8) **搜索升级：FTS5（可选）**
- 你已确认可以接受搜索更慢以换取灵活性，因此不建议把默认匹配改为前缀匹配。
- 若未来数据规模继续增长到搜索不可接受，再考虑引入 SQLite FTS5（filename/author/description），实现更快的全文检索。

9) **解除“单连接 + mutex”导致的读写串行化**
- 做法：
  - 引入“读连接/写连接”分离（至少 2 个连接），读操作使用读连接；写操作（导入/删除/更新描述）使用写连接。
  - 或对每次 command 打开短连接（以 db path 为 key 缓存/池化），避免所有请求在应用层互斥。
- 验收：导入过程中，列表浏览/搜索/排序不再被明显拖慢。

10) **导入批处理事务化**
- 文件：[import.rs](file:///d:/dev/littlefile/src-tauri/src/commands/import.rs)
- 做法：
  - 每 `batch_size` 使用一笔 transaction 批量插入（并复用 prepared statement）。
  - 去掉每文件 `SELECT COUNT(*)` 的重复查询：对 sha256 做 UNIQUE 约束，插入使用 `INSERT OR IGNORE` / `ON CONFLICT` 策略匹配 dedup_strategy。
- 验收：导入吞吐显著提升；并减少导入期间 DB 锁争用时间窗口。

## Assumptions & Decisions（已确认）
- 状态栏文件数：显示“当前/总计”。
- 排序行为：点击后立即重排并回到顶部。
- 卡顿阶段：导入中与导入后都慢。

## Verification（验收/验证步骤）
- 功能：
  - 搜索栏输入关键字：状态栏显示 `当前/总计`，且当前值与 `list_files.total_count` 一致。
  - 清空搜索：当前值回到总计。
  - 点击排序列：列表立即重排并回到顶部；后续加载更多顺序保持一致。
  - 导入完成：状态栏总计立刻变化；列表可正常刷新。
  - 删除文件：状态栏总计立刻变化。
- 性能（定性 + 可量化）：
  - 2万文件库：打开库后首屏渲染与滚动加载更多无明显卡顿。
  - 点击排序列的响应时间显著下降（至少不再“无反馈”）。
  - 导入进行中：列表仍可搜索/排序，延迟可接受（重点观察 mutex/DB 争用改善后效果）。
